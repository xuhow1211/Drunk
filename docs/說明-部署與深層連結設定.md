# 部署與深層連結設定說明

> 用途：說明本專案在不同靜態託管平台上部署時，如何讓 `/recipe/negroni`、`/match`
> 這類前端深層連結在「直接開新分頁」或「重新整理頁面」時不會出現 404。

## 一、為什麼需要這份設定

本專案的路由由 `react-router-dom` 在瀏覽器端處理，但部署出來的是一份靜態網站。
靜態主機收到 `/recipe/negroni` 這個路徑時，會到檔案系統上找 `recipe/negroni` 這個檔案；
找不到就直接回應 404，使用者看到的就是「頁面不存在」，而不是預期中的配方頁。

解法是讓所有「找不到實體檔案」的路徑都回到 `index.html`，
再由前端路由依照網址把它渲染成正確的頁面。這就是所謂的 SPA rewrite。

## 二、各平台的設定檔

| 平台 | 設定檔 | 狀態 |
|------|--------|------|
| Netlify | `public/_redirects` | 已提供 |
| Cloudflare Pages | `public/_redirects` | 已提供（與 Netlify 共用同一份語法） |
| Vercel | `vercel.json` | 已提供 |
| GitHub Pages | 無通用解法 | 需另外處理，見下方說明 |

### `public/_redirects`

Netlify 與 Cloudflare Pages 會自動把 `public/` 底下的檔案原樣複製到輸出目錄，
因此這份檔案會隨著建置產物一起部署。檔案內容除了轉址規則本身，
也以 `#` 開頭的註解寫明了作用與限制。

規則本體只有一行：

```
/*    /index.html   200
```

`200` 的意思是「以 200 狀態碼回傳目標內容」，而不是真的轉址，
因此瀏覽器網址列不會改變，分享連結時也會保留原本的 `/recipe/negroni`。

### `vercel.json`

Vercel 使用自己的設定格式，因此另建 `vercel.json`：

```json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}
```

Vercel 的 `rewrites` 會在「檔案系統找不到對應檔案」之後才套用，
所以 Vite 產出的 `/assets/index-XXXX.js`、`/assets/index-XXXX.css` 這類帶雜湊的檔名
仍會正常輸出，不會被轉址吃掉。

### GitHub Pages

GitHub Pages 不支援上述任何一種轉址語法。常見的 workaround 是在分支根目錄放一份
`404.html`，把內容複製自 `index.html`，讓 GitHub Pages 在找不到檔案時以 404 狀態
回傳這份頁面，前端再從 `location.pathname` 還原路由。

**本專案刻意不採用這個做法**，原因如下：

1. 該頁是以 HTTP 404 狀態回應的，搜尋引擎會把它判定為「不存在的內容」，
   對 `/recipe/negroni` 這類頁面的 SEO 有負面影響。
2. 使用者按下「重新整理」時會看到瀏覽器明確的 404 畫面，體驗不佳。

若最終要部署到 GitHub Pages，建議改用 Hash 路由（`react-router-dom` 的
`createHashRouter`），把路由變成 `/index.html#/recipe/negroni`，
如此一來所有路徑都指向同一份實體檔案，不需要任何主機端設定。
這是一項會影響全站連結格式的變更，需另行評估後再進行。

## 三、本地驗證

建置後可用 `npm run preview` 起在本機靜態伺服器，
再以 `curl` 確認深層連結會回傳 `index.html`：

```
npm run build
npm run preview
curl -I http://localhost:4173/recipe/negroni
```

預期結果：`HTTP/1.1 200 OK`，且回應內容為 `index.html`。
